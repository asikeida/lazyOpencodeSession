# 为什么删除前应该展示影响范围

> 实施状态（2026-09-03）：最小方案已经完成。确认框异步展示 session/message/part 数量，确认时在短事务内重新统计，范围变化会中止删除并刷新数据。

## 结论

如果 `lazyocs` 只供作者自己使用，这项功能可以暂缓；但只要项目准备公开发布，并保留“永久递归删除”能力，我认为它有必要。

理由不是“删除功能应该做得更华丽”，而是当前界面表达的操作对象和数据库实际删除的对象并不完全一致：

```text
用户看到：删除当前 session
数据库执行：删除当前 session + 全部子 session + 关联 message + 关联 part
```

确认框只有在准确说明后果时才是有效的安全措施。否则它只是多按一次 `y`。

## 当前已经安全在哪里

当前删除实现并不粗糙，已经具备多项重要保障：

- 使用参数化 SQL，session ID 不会被拼接进查询。
- 使用递归 CTE 删除完整子树，不会留下孤立子 session。
- 使用 `UNION` 去重，异常 parent 环也能收敛。
- 删除由单条 SQL 完成，具备原子性。
- `message -> session` 和 `part -> message` 依靠外键级联删除。
- 启动时检查 Schema 和级联关系，不满足要求时 fail closed。
- 只读模式通过 SQLite `mode=ro` 从数据库层禁止写入。
- 删除需要二次确认，失败后确认框仍可重试或取消。

这些措施解决的是“程序能否正确删除”和“数据库结构是否安全”。

它们没有解决另一个问题：用户是否知道自己将删除多少内容。

## 真正的风险不是 SQL 错误，而是意图错误

数据库写操作通常有两类风险。

| 风险 | 示例 | 当前状态 |
| --- | --- | --- |
| 执行安全 | SQL 注入、半删、外键失效、只读模式失效 | 已有较强保护 |
| 意图安全 | 用户以为删一条，实际上删掉一棵 session 树 | 尚未充分说明 |

Schema 检查可以证明：

> 这条删除语句可以按照设计执行。

但它不能证明：

> 用户理解并接受这条删除语句的影响范围。

对于不可撤销操作，后者同样重要。

## 当前确认框为什么还不够

改造前确认框只展示：

```text
此操作将永久删除该会话及其所有子会话。
目标: 当前标题
ses_xxx
y / Enter 删除    n / Esc 取消
```

文字已经提到子会话，这是正确的；问题在于“所有”是抽象描述。

下面两种操作在当前界面中的视觉重量几乎相同：

```text
情况 A：删除 1 个 session，没有子 session
情况 B：删除 1 个根 session、17 个子 session、数千条消息
```

用户只有在删除后才会发现二者差异，而删除目前没有撤销能力。

## 最小方案，不需要做成复杂系统

我不建议第一版加入回收站、审计服务、后台任务或复杂图表。最小有效方案只需要在打开确认框后异步查询三个数字：

```text
将永久删除：
  Sessions  4（当前 1 + 子会话 3）
  Messages  126
  Parts     482
```

用户需要知道的是“范围”，不是数据库内部的每一行。

### 建议展示

- session 总数。
- 其中子 session 数量。
- message 数量。
- part 数量。
- 根 session 标题和 ID。

### 第一版不建议展示

- 不计算 `sum(length(data))`。
- 不读取 message/part JSON 内容。
- 不列出所有子 session 标题。
- 不生成可视化树。
- 不顺便实现备份或回收站。

尤其不建议默认计算 payload 字节数。真实数据库约 3.1GB，`length(data)` 可能扫描大量内容；删除确认不应该因为一个“看起来很专业”的体积数字变慢。

## 查询成本可以控制

可以复用删除语句已经使用的递归 CTE，只统计行数：

```sql
with recursive descendants(id) as (
  select id from session where id = ?
  union
  select s.id
  from session s
  join descendants d on s.parent_id = d.id
)
select
  (select count(*) from descendants),
  (select count(*) from message where session_id in (select id from descendants)),
  (select count(*) from part where session_id in (select id from descendants));
```

这个查询有几个重要边界：

- 只读取 ID 和索引，不读取 JSON payload。
- 继续使用 `UNION`，不会被 parent 环无限递归。
- 在用户按 `d` 后异步执行，不阻塞 Bubble Tea 事件循环。
- 没有统计结果前不允许确认删除，但允许 `Esc` 取消。
- 查询失败时禁止删除，而不是显示未知范围后继续执行。

已使用 `EXPLAIN QUERY PLAN` 检查真实 OpenCode 数据库：递归查询使用 `session_parent_idx`，message 使用 `message_session_time_created_id_idx`，part 使用 `part_message_id_id_idx`。一次实际统计得到 4 个 session、750 条 message 和 3566 条 part，耗时约 8ms，且没有读取 JSON payload。

## 如何处理“确认后数据又变化”

影响范围查询和用户按下确认之间存在时间窗口。此时 OpenCode 可能继续写入新的消息或子 session。

不需要长时间持有数据库事务等待用户输入。更简单的规则是：

1. 打开确认框时查询一次影响范围。
2. 用户确认后，在短事务中重新计算范围。
3. 如果 session/message/part 数量发生变化，中止删除并要求重新确认。
4. 数量一致时，在同一事务中执行删除并提交。

这样不会因为用户停留在确认框中而长期锁库，也不会拿着过期数字执行删除。

如果第一版想进一步缩小实现范围，也可以只重新校验 session 总数。至少应避免在“原本没有子 session，确认前突然新增子 session”的情况下静默扩大删除范围。

## Before / After

### Before

```text
按 d
  -> 显示标题和 ID
  -> 用户看到抽象的“所有子会话”
  -> 按 y
  -> 递归删除未知数量的数据
```

### After

```text
按 d
  -> 异步统计影响范围
  -> 明确显示 4 sessions / 126 messages / 482 parts
  -> 用户基于具体范围确认
  -> 删除前快速重新校验
  -> 范围一致才执行删除
```

## 为什么不是先做自动备份

自动备份的保护能力更强，但实现成本和产品决策也更大：

- WAL 模式下不能只复制主 `.db` 文件。
- 需要决定备份位置、命名、保留周期和清理策略。
- 需要处理磁盘空间不足。
- 需要设计恢复入口，否则备份只是隐藏文件。
- 3.1GB 数据库的完整备份可能明显延迟一次删除。

影响范围展示不能代替备份，但它是成本更低、没有额外存储、直接改善用户决策的一层保护。合理顺序是：

```text
先让用户知道会删什么
  -> 再根据真实需求决定是否提供备份和恢复
```

## 哪些情况下可以不做

以下任一条件成立时，可以合理地不实现：

- 删除功能不对外发布。
- 工具改为只读浏览器。
- 删除只允许删除没有子 session 的叶子节点。
- 每次删除都有可靠、可验证且易恢复的自动备份。
- OpenCode 自身提供官方删除 API，并负责展示和确认影响范围。

当前这些条件都不成立：lazyocs 默认可写、删除不可撤销，而且直接操作上游 SQLite schema。

## 成本与收益

| 项目 | 评价 |
| --- | --- |
| 新增概念 | 一个 `DeleteImpact` 结果和对应异步消息 |
| 数据库复杂度 | 复用现有递归 CTE，只增加计数 |
| UI 复杂度 | 确认框增加数行文本和 loading/error 状态 |
| 性能风险 | 可通过不读取 payload、检查索引来控制 |
| 用户收益 | 删除前知道真实范围，显著降低误删概率 |
| 项目收益 | 补齐不可逆操作的意图安全，而不只是 SQL 安全 |

这是一个“小代码量、高风险覆盖”的功能，比继续增加筛选条件或界面装饰更值得优先完成。

## 建议验收标准

- 删除叶子 session 时显示 `1 session`。
- 删除根 session 时准确包含全部后代。
- parent 环不会导致统计无限递归。
- message 和 part 只统计行数，不读取 payload 内容。
- 统计在 `tea.Cmd` 中执行，TUI 始终可以取消。
- 统计失败时删除按钮不可确认。
- 确认前范围发生变化时中止并要求重新确认。
- 只读模式不会执行影响查询后的任何写操作。
- 正式 `Open()` 集成测试覆盖统计与实际删除结果一致。

## 最终说服理由

我建议做，但只做最小版本。

不是因为每个删除按钮都需要复杂预览，而是因为 lazyocs 的“一个删除动作”可能跨越多层数据：session 子树、message 和 part。程序已经投入成本保证递归删除和级联删除执行正确；如果不把这个真实范围告诉用户，安全链条仍缺少最后一环。

一句话概括：

> Schema 检查保证程序删得正确，影响范围展示保证用户确认的是自己真正要删的东西。
